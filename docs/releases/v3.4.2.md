# v3.4.2

Patch-Release mit genau einem Thema: das Selbst-Update. Es lief auf keiner systemd-Installation durch, und weil der Endpunkt seinen Erfolg meldet, bevor der erste Schritt läuft, sah jeder Fehlschlag in der Oberfläche aus wie ein gestartetes Update. Aufgefallen ist das erst, als beide Homelab-Instanzen Wochen nach einem Release immer noch auf der alten Version standen.

## Highlights

- **`git pull` brach dauerhaft ab** (#335): `install.sh` und der Ansible-Deploy führen beide `npm install` im Checkout aus, das schreibt `package-lock.json` um — und ein Pull verweigert danach die Arbeit („Your local changes would be overwritten by merge"). Ein Deployment-Verzeichnis ist keine Arbeitskopie; der Abgleich läuft jetzt über `git fetch` + `git reset --hard FETCH_HEAD`. Nur nachverfolgte Dateien sind betroffen, das Datenverzeichnis ist gitignoriert und unversionierte Altlasten bleiben liegen.
- **`NODE_ENV=production` entfernte die Build-Toolchain** (#335): Die systemd-Unit setzt es, npm liest es als `--omit=dev` und *entfernt* `tsup`/`vite`/`typescript` — exakt die Binaries, die die folgenden vier Schritte aufrufen. Im Journal stand dazu eine einzige Zeile (`sh: 1: tsup: not found`); zurück blieben neue Quellen, keine Toolchain und das alte `dist/` im Betrieb. Das war der gefährlichere der drei Fehler. Die Kindprozesse laufen jetzt ohne `NODE_ENV` — entfernt statt auf `development` gesetzt, damit npm und die Build-Tools ihre eigenen Defaults behalten; `vite build` setzt den Production-Mode ohnehin selbst.
- **Der Ausgang ist jetzt sichtbar** (#335): Jeder Schritt wird in `data/update_state.json` protokolliert und über den neuen, admin-geschützten Endpunkt `GET /api/update/status` ausgeliefert. Beide Oberflächen pollen ihn und zeigen am Ende die neue Version oder den gescheiterten Schritt samt `stderr`-Ende. Was dabei *nicht* funktioniert: die Schritte laufen über `spawnSync` und blockieren den Event-Loop, der Endpunkt antwortet während eines Updates also gar nicht — die Anzeige des gerade laufenden Schritts ist damit unerreichbar, auch wenn sie implementiert ist. Aufgefallen ist das erst beim End-to-End-Test, nachgetragen als #338. Weil die Statusdatei im `DATA_DIR` liegt, überlebt sie den Neustart am Ende eines erfolgreichen Updates — das Ergebnis ist also auch danach noch abrufbar. Ein `running`-Zustand älter als 20 Minuten gilt als fehlgeschlagen, weil ein vom OOM-Killer beendeter Build nie einen Endzustand schreibt.
- **Zwei Lücken in der Oberfläche** (#335): Einstellungen → Sync prüfte `res.ok` beim Update-Aufruf nie, ein abgelehnter Schlüssel wurde dort als „Update gestartet" angezeigt. Und ein Update, das scheiterte, während der Admin-Tab geschlossen war, hinterließ keine Spur — der letzte fehlgeschlagene Versuch wird jetzt beim Öffnen der Admin-Seite angezeigt.
- **Der Web-Build wird über ein Staging-Verzeichnis ausgetauscht**, statt `public/` erst zu löschen und dann hineinzukopieren. Ein Kopiervorgang, der auf halber Strecke abbrach, ließ die Web-App vorher mit 404 zurück; ein fehlender Build bricht das Update jetzt ab, statt den Server kommentarlos auf einem gescheiterten `build:web` neu zu starten.

## Getestet

- Neue Server-Testsuite `update.test.ts`: 24 Fälle. Sie prüfen die *Argumente und die Umgebung*, die die Schritte bekommen — dass kein `pull` mehr vorkommt, dass `NODE_ENV` in keinem Kindprozess ankommt, dass der Lauf beim ersten Fehler stoppt und festhält an welchem Schritt, dass der Zustand bis zum Status-Endpunkt durchkommt. Genau diese Ebene fehlte: die drei Fehler waren umgebungsbedingt und hätten jeden Test bestanden, der die Schritte in einer Dev-Shell ausführt.
- Server-Testsuite gesamt: 240/242 grün. Die zwei Fehlschläge sind dieselben Windows/NTFS-Artefakte wie in 3.4.0 und 3.4.1 (`chmod 0600` ist auf NTFS nicht darstellbar), unverändert und auf Linux grün.
- Alle Pflicht-Checks auf PR #336 grün (build, build-android, CodeQL, Analyze, claude-review). Der automatische Review fand in der ersten Fassung einen echten Fehler — die Admin-Seite übernahm beim Laden nur einen laufenden, keinen gescheiterten Lauf; behoben und als eigener Commit nachgezogen.
- **End-to-End auf der Test-Instanz verifiziert**: Instanz auf den Fix gebracht, `package-lock.json` absichtlich verschmutzt und damit exakt der Zustand hergestellt, an dem der alte Pull scheiterte (`error: Your local changes ... would be overwritten by merge`, bei verfügbarem neuem Commit) — unter derselben `NODE_ENV=production`-Unit, die den alten Weg zerlegt hat. Update über `POST /api/update/apply` ausgelöst: 8/8 Schritte in 30,5 s, `phase: success`, Neustart, `3.4.1` → `3.4.2`, Arbeitskopie danach sauber. Derselbe Lauf hat #338 zutage gefördert — während der 30,5 s beantwortete der Server keinen einzigen Poll, weil `spawnSync` den Event-Loop hält.
