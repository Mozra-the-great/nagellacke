# v3.4.0

Self-Registration in der Web-App, signierte Foto-Zugriffs-Tokens, der Sync-Refresh-Token als httpOnly-Cookie, ein Multi-Stage-Docker-Build für Cloud-Deployments sowie eine Reihe von Sicherheits- und Barrierefreiheits-Fixes seit 3.3.0.

## Highlights

- **Self-Registration im Web-Login** (#295): Das Sync-Login-Formular zeigt ein Registrieren-Feld, sobald der Server das erlaubt (`GET /api/auth/registration-status`, gedeckt durch den zentralen `registrationOpen()`-Helfer). Ältere Server verhalten sich unverändert.
- **Fotos hinter einem signierten Zugriffs-Token** (#285): `/photos/*` ist nicht mehr öffentlich — Zugriff über `X-Api-Key`, Bearer-JWT oder einen signierten `?t=`-Query-Token, mit Revokation über `token_version`.
- **Sync-Refresh-Token als httpOnly-Cookie** (#307): Der Web-Client hält keine Tokens mehr in `localStorage`; ein Reload holt sich über das Cookie einen frischen Access-Token, ohne als Logout zu wirken.
- **`v3/Dockerfile` für Cloud-Deployments** (#321): Multi-Stage-Build (`node:20-alpine`), unabhängig vom bestehenden `install.sh`/systemd-Weg für self-hosted LAN-Installs.
- CI baut ab sofort das Android-Modul auf jedem Pull Request (#302); `fixtures/merge/*.json` ist der von Web/Server und Android geteilte Testvertrag für `mergeData()`/`Merge.kt`.

## Sicherheit

- Registration-Status-Check ignorierte ein absichtlich leeres Server-URL-Feld (#325)
- Android: `resolveWithin` lehnt absolute Foto-Dateinamen aus dem Sync ab
- `ai_jobs.json`-Dateiberechtigungen gehärtet, Login-Timing-Seitenkanal geschlossen (#292)
- 2FA-Deaktivierung ohne aktives 2FA wird jetzt abgelehnt (#288)
- Benutzername-Längenbegrenzung gegen HTTP-431-Bricking (#287)
- Datei-Rechte, E-Mail-Versand, Login-Lockout, `npm audit`-Funde aus einem QA-Durchlauf gehärtet (#262)
