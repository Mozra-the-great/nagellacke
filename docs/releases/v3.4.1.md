# v3.4.1

Patch-Release: zwei Fehler rund um die Foto-Authentifizierung, die beide erst im laufenden Betrieb sichtbar wurden — ein veralteter API-Schlüssel, der eine gültige Sitzung überstimmte, und ein Rate-Limit, das zwar deklariert war, aber nie griff.

## Highlights

- **Foto-Upload scheiterte dauerhaft mit einem nackten `401`** (#330): Lag im Browser ein API-Schlüssel, den der Server nicht mehr kennt, überstimmte er die intakte Server-Sitzung — `authHeaders()` bevorzugte ihn bedingungslos, und serverseitig betrachtet `requireApiKeyOrJwt` einen mitgeschickten Schlüssel als die einzige Anmeldung, die es prüft. Ohne Fallback, ohne Refresh, ohne verwertbare Meldung. Ein abgelehnter Schlüssel wird jetzt einmal durch das JWT ersetzt und danach nicht mehr gesendet; bleibt nur er übrig, benennt die Meldung den tatsächlichen Auslöser statt eines Statuscodes.
- **Die Schlüssel-Rotation räumt ihre eigene Spur auf** (#330): Bisher ließ die Rotation im Admin-Panel genau den Schlüssel im `localStorage` liegen, den der Aufruf gerade entwertet hatte — die häufigste Ursache des Fehlers oben. Er wird jetzt entfernt und bewusst *nicht* durch den frischen ersetzt: Rotation existiert, um eine geleakte Kopie zu verbrennen.
- **Fotos zielten im Cross-Origin-Betrieb auf den falschen Host** (#330): `photos.ts`/`photoToken.ts` waren die letzten Module mit nackten relativen Pfaden. Upload, Token-Abruf und die `<img>`-Quellen laufen jetzt wie alles andere über die konfigurierte `serverUrl` — relevant für „Eigener Server" und das Container-Deployment, wirkungslos für Same-Origin-Installationen.
- **Sicherheit: Das Rate-Limit auf `GET /api/photos/token` war wirkungslos** (#332): Die Route stand über `register(rateLimitPlugin, …)`, und `@fastify/rate-limit` liest die Route-Config in einem `onRoute`-Hook, der nur für danach registrierte Routen feuert. 70 Requests, kein einziger 429. CORS war trotz derselben Reihenfolge nie betroffen — genau diese Asymmetrie hat den Fehler verborgen und steht jetzt als Kommentar neben der Route.
- **`nodemailer` auf 9.1.1** (vorher 9.0.5): schließt vier offene High-Advisories (Bypass von `disableFileAccess`/`disableUrlAccess` über die Legacy-Signatur von `resolveContent()`, zwei Umgehungen der Empfänger-Domain-Prüfung via IDN/Punycode bzw. RFC-5322-Kommentare, quadratische Laufzeit im `addressparser`). Reine Lockfile-Änderung, die bestehende Range `^9.0.3` deckte die Version bereits ab. `npm audit --omit=dev` meldet damit 0 Funde.

## Getestet

- Web-Testsuite: 34/34 grün, inklusive neuer Fälle für den JWT-Fallback bei totem Schlüssel, das Nicht-erneut-Senden eines abgelehnten Schlüssels, das Verwerfen des zwischengespeicherten Foto-Tokens und die Cross-Origin-URL-Auflösung.
- Server-Testsuite: 216/218 grün. Die zwei Fehlschläge sind dieselben Windows/NTFS-Artefakte wie in 3.4.0 (`chmod 0600` ist auf NTFS nicht darstellbar), kein Regressionsfehler — CI läuft auf Linux und ist grün.
- Der Regressionstest für #332 wurde gegen den alten Code gegengeprüft: dort schlägt er fehl (`expected null to be 61`), auf dem Fix läuft er. Vorher deckte kein einziger Test einen Rate-Limiter ab.
- Alle Pflicht-CI-Checks (build, build-android, CodeQL, claude-review) grün auf PR #331 und #333.
